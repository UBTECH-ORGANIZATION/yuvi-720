תקציר

ביצענו הליכה מלאה בכל חמשת רכיבי היחידה (-01 עד -05), כולל פתרון נכון של כל השאלות עד להשגת כשירות ביעד הלמידה. במהלך ההרצה תועדו 12 ממצאים בצד התוכן. שלושה מהם חמורים ודורשים טיפול לפני פריסה לתלמידים — ובראשם דליפת אסימון הכתיבה ל־LRS אל Google/YouTube.

כל ממצא בדוח מלווה בעדות גולמית: הצהרת xAPI מלאה כפי שהתקבלה אצלנו, או קוד המקור של התוכן עצמו. הפלטפורמה שלנו כבר הותאמה כדי לצמצם את הנזק בצד שלנו, אך אלה תיקונים שרק ספק התוכן יכול לבצע בשורש.

ממצאים קריטיים

קריטי · אבטחה 1. אסימון הכתיבה ל־LRS של הלומד נמסר ל־Google

התוכן מקבל את הרשאות הדיווח דרך פרמטר slxapi במחרוזת השאילתה של כתובת הדף. אותו דף מטמיע נגן YouTube, ו־YouTube IFrame API מוסיף אוטומטית את כתובת הדף המלאה לכתובת ה־iframe בפרמטרים forigin ו־widget_referrer. התוצאה: אסימון ה־Bearer, כתובת ה־LRS, מזהה הלומד וה־registration נשלחים לשרתי Google בכל טעינת מסך וידאו.

קוד המקור של התוכן — כך זה קורה

הפונקציה מוסיפה במפורש את הכתובת המלאה של הדף, זו שמכילה את האסימון:

/* lomdot.education.gov.il/…/methodica-science-mass-measure-01-04/index.html */
function ytEmbedPlayerVars() {
  const vars = { rel: 0, modestbranding: 1, playsinline: 1,
                 hl: 'iw', cc_lang_pref: 'iw', cc_load_policy: 1 };
  if (/^https?:$/.test(window.location.protocol)) {
    vars.origin          = window.location.origin;
    vars.widget_referrer = window.location.href;   // ← כולל ?slxapi={…"auth":"Bearer …"}
  }
  return vars;
}

השפעה
  • מי שמחזיק באסימון יכול לכתוב הצהרות xAPI שרירותיות בשם אותו לומד אל kata.cet.ac.il.
  • מזהה הלומד וה־mbox נמסרים לצד שלישי מסחרי — בניגוד להנחיות הפרטיות של תוכנית 720.
  • הדליפה מתרחשת גם דרך כותרת Referer רגילה לכל משאב חיצוני שנטען מאותו דף.
מה נדרש מ־Kata
  1. להוציא את slxapi ממחרוזת השאילתה. להעביר את הרשאות הדיווח ב־postMessage מהפלטפורמה המארחת, או למשוך אותן בבקשת שרת נפרדת לאחר טעינת ה־iframe.
  2. עד לתיקון: להסיר את vars.widget_referrer, להוסיף <meta name="referrer" content="no-referrer"> לדף התוכן, ולשלול את היכולת של ה־iframe החיצוני לקרוא את כתובת האב.
  3. לבטל ולהנפיק מחדש את כל אסימוני ה־LRS שהונפקו עד כה.
  4. לקצר את תוקף האסימון ולהגביל את הרשאתו לכתיבה לרכיב ולרישום הספציפיים בלבד.

קריטי · חסימה 3. סיום הרכיב חסום מאחורי YouTube

במסך הווידאו של רכיב -04, כפתור «להמשיך» נשאר מנוטרל עד ש־YouTube מדווח PlayerState.ENDED. אין מסלול חלופי. 

function s8Enter() {
  const cont = document.getElementById('s8-continue');
  if (s8Done) { cont.disabled = false; }
  else        { cont.disabled = true; … initS8Player(); }   // אין דרך אחרת לפתוח
}

function initS8Player() {
  loadYouTubeApi(function () {            // ← אם הסקריפט חסום, ה-callback לא ירוץ לעולם
    s8YtPlayer = new YT.Player('s8-youtube-player', { …
      events: {
        onStateChange: e => { if (e.data === YT.PlayerState.ENDED) s8OnVideoEnded(); },
        onError:       () => s8OnVideoEnded()   // ← מטופל רק כשל של הנגן, לא כשל טעינת ה-API
      } });
  });
}

onError אכן משחרר את החסימה — אבל הוא רץ רק אחרי ש־YT.Player נבנה בהצלחה. כאשר סקריפט ה־API עצמו חסום (חומת אש בית־ספרית, או מדיניות משרד החינוך שאוסרת YouTube), loadYouTubeApi לא מסתיים, הנגן לא נבנה, ואף אחד משני ה־callbacks לא נורה. הלומד נתקע ואינו יכול לסיים את הרכיב — ולכן גם לא להגיע לשאלת השיא.

מה נדרש מ־Kata

להוסיף timeout סביב טעינת ה־API שמשחרר את החסימה, ולהעדיף על פניו את התיקון בממצא 2 — וידאו מקומי אינו יוצר תלות חיצונית כלל.

ממצאים בחומרה בינונית

בינוני 7. question_count בקטלוג סותר את מספור השאלות בנגן

הפלטפורמה מכתירה את שיחת הליווי לפי מטא־דאטה מהקטלוג, אבל הנגן מציג ללומד מספור אחר. כתוצאה מכך הצ'אט מדבר על «שאלה 5» בזמן שעל המסך כתוב «שאלה 3».

בינוני 8. מסכי וידאו אינם מדווחים אירוע ברמת הפריט

ברכיב -04 יש שישה פריטים, אך לאורך כל ההרצה התקבלו אירועים עבור -001 עד -005 בלבד. פריט -006 (מסך הווידאו) לא שלח initialized ולא completed. אותה תופעה נצפתה ב־-01-003: 90 שניות של צפייה ללא אף אירוע ברמת המסך.

בלי אירוע כזה הפלטפורמה אינה יודעת שהלומד הגיע למסך, והמלווה הדיגיטלי נשאר תקוע על השאלה הקודמת. זו הסיבה שנאלצנו להסיק מיקום מתוך פעלי מדיה — מה שמתנגש עם ממצא 6.

בינוני 9. אין אירוע במעבר בין סעיפים בתוך פריט

בפריט -02-001 יש שני סעיפים. המעבר מסעיף א לסעיף ב אינו מייצר אף הצהרה — הפלטפורמה מגלה את המעבר רק כאשר מגיע answered עם q2, כלומר אחרי שהלומד כבר ענה. עד אז הליווי מציג הקשר של הסעיף הקודם.

מה נדרש מ־Kata

לשלוח enter עם questionId בכל מעבר סעיף, כפי שנשלח במעבר בין פריטים.

ממצאים בחומרה נמוכה

נמוך 10. completed נשלח ללא questionId

כל שאלה מדווחת פעמיים: answered ואחריו completed. ל־answered יש questionId, ל־completed אין. במסך שנושא כמה סעיפים לא ניתן לשייך את הסיום לסעיף הנכון, ואנו נאלצים לגזור זאת מהקשר.

נמוך 11. אזורי role="status" ישנים נשארים ב־DOM

ברכיב -05, לאחר ארבעת הסעיפים, נמצאו ארבעה אזורי role="status" — אחד גלוי והשאר מוסתרים ויזואלית אך עדיין נושאים את נוסח המשוב הישן. קורא מסך מונה את כולם, כך שהלומד עלול לשמוע משוב של סעיף קודם.

לבירור 12. הנתון באיור אינו תואם לנתון בטקסט

ברכיב -05, סעיף א, טקסט השאלה מציין שקילה של 682.4 גרם לפני ואחרי, בעוד שהאיור הנלווה מתואר כ«המאזניים מציגים 675.2 גרם». ייתכן שהאיור כללי בכוונה, אך בשאלה שכל כולה קריאת ערכי שקילה זה עלול לבלבל. נבקש אישור שזו התנהגות מכוונת.
